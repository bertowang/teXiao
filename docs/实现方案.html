需求与数据流总览

Requirements & Data Flow
一页看懂：0.1 说明要做的东西是什么、给谁用、输入输出是什么；0.2 用一张图画出数据从宿主进来到画面出去经过的全部处理节点；0.3 逐个节点说明职责；0.4 用一句话说清图里的「Graph 编译」。后续章节都是对这张图的展开。

0.1 需求说明

要做什么：一个嵌入宿主 App（拍摄、直播、视频编辑）的跨平台实时特效引擎。宿主送入相机帧或视频帧，引擎按「特效素材」的描述在 GPU 上逐帧处理（美颜、滤镜、贴纸、AI 驱动的形变等），再把结果交还宿主或直接上屏。引擎只做处理，不负责采集、编码和 UI。

输入（宿主提供）

  • 每帧的 GPU 纹理 + 时间戳 t（相机 pts 或视频时间）
  • 纹理形态与方向：OES / NV12 / RGBA，旋转、镜像
  • 特效素材 JSON 及其资源（LUT、贴纸图、模型）
  • 运行时参数：如美颜强度
→

引擎（本文要设计的部分）

  • 加载期：校验素材，编译成渲染图
  • 每帧：归一化输入 → 跑效果链 → 输出
  • 异步：AI 推理，结果供效果读取
  • 全程 GPU 零拷贝，按 t 确定性出图
→

输出（交还宿主）

  • 直接上屏（Surface / Layer / 窗口）
  • 或结果纹理 ID，供宿主继续编码 / 合成
  • 或显式回读像素（测试、截图）

0.2 数据流简图

数据沿三条泳道流动：加载期把素材编译成可执行的渲染图（每个素材一次）；每帧在渲染线程上把输入纹理推过效果链；AI 在后台线程异步推理，结果以快照形式供效果读取，渲染从不等待它。

读图要点：主链从左到右只传 GPU 句柄；NormalizePass 之后所有节点只面对标准 RGBA8；AI 从主链「分叉」出去、再以只读快照「汇入」效果链，两条路径之间没有等待。

0.4 概念补注：Graph 编译是什么

0.2 的图里有「Graph 编译」和「已编译 Graph」，0.3 的表里也有「Graph 编译」一行。0.4.1 用一句话说清概念，0.4.2 给出具体的数据结构骨架，都不用先读第 05 章。

0.4.1 一句话理解

「编译」不是编译 C++ 代码，而是把人写的素材 JSON，提前整理成引擎每帧能直接照着做的执行清单。这份清单就是「已编译 Graph」。加载素材时做一次，之后每帧只照单执行。
打个比方

菜谱 → 备菜

素材 JSON 像菜谱：「先磨皮、再调色、最后贴贴纸」。厨房不会每来一桌客人都重读菜谱、找调料、想顺序；而是开业前把步骤排好、调料分装、盘子编号。出餐时只按编号取用。备菜 = 编译，分装好的料 = 已编译 Graph。

为什么要提前做

每帧只有 33ms

解析 JSON、按字符串找 Shader、临时决定用哪张中间纹理，都是慢活，放在 30fps 的热路径里必然掉帧。所以把这些「一次性的思考」挪到加载期，运行时只剩数组遍历和 GPU 调用。

编译前 → 编译后（同一个磨皮效果） 
// 素材 JSON：人写的，全是字符串
{ "id":"beauty", "shader":"beauty/soft_skin",
  "in":"rt0", "out":"rt1", "params":{ "strength":0.6 } }

// 已编译 Graph：内存里的一张表，每帧直接读
Pass[1] = { shader = handle#12, in = fbo#1, out = fbo#2,
            strength = paramTable[7] }   // 名字全变成句柄 / 下标

「编译」这一步具体只做三件事：

① 排顺序、查错按 in/out 排出执行先后；成环、引用了不存在的资源，加载期就报错拓扑排序
② 规划中间纹理算出每张中间图的存活区间，不重叠的共用同一块 FBO5 个 Pass 常只需 2~3 张
③ 名字变下标Shader 名 → 句柄，参数名 → 数组下标运行期不再查字符串
两个常见误会：① 产物不是 .cpp、不是机器码、也不写磁盘，只是内存里的结构体（即图中的 AssetRuntime）；② 调参数不用重编译，SetParam 和时间轴只改表里那个数值，换素材或素材结构变了才重编译。另注意：5.4 的「代码生成」是构建期用 Python 生成 C++，与此处的运行期 Graph 编译是两回事。

如果只是理解概念，读到这里就够了；0.4.2 说说它内部大致怎么组织。

0.4.2 编译结果用什么数据结构存

答案：不是一张用指针连起来的图，而是几张顺序排列的「表」，彼此用序号互相引用。它只是一份常驻内存、加载后只读的数据，归素材级的运行时对象持有；不生成代码文件，也不写磁盘。

下面只讲通用的组织思路，不对应任何既有工程的具体实现；各张表的名字也只是便于称呼，落地时可自行命名。

编译结果里一共四张表：

表存什么为什么需要
执行顺序表按先后排好的一串步骤。每一步写明：用哪个效果、读哪几张中间图、结果写到哪张中间图、参数在数值数组的哪一段，以及「是最终输出」「已降级为空操作」等标记每帧从头到尾走一遍即可，不必再判断顺序，也不必解析名字
中间图登记表每张逻辑中间图的尺寸、格式、首次写入与末次读取的位置，以及它对应哪一块可复用的物理画布用完的画布能借给后面的步骤，控制显存峰值
静态资源表已加载好的 LUT、贴纸图等纹理步骤里只记序号，需要时直接取
参数布局表每个参数固定对应数值数组里的一个位置；具体数值不放在这里调参数、播动画只改数值，不用重做编译

「物理画布」可以理解成一组能反复擦写的画板：逻辑中间图只是记录「第几步写到哪块画板」，两张生命周期不重叠的中间图可以共用同一块画板。

每帧怎么消费这份结果：

① 取下一步按顺序表读下一条记录，顺序早已排定不排序、不比较字符串
② 找画布用记录里的中间图序号查登记表，得到画板编号，从资源池取用不新建资源，用完归还
③ 取参数执行按记录里的参数区间，从数值数组取一段交给对应效果效果本身不保存跨帧状态
④ 继续下一步本步输出即下一步输入，直到最终输出整帧就是一次线性遍历

为什么普遍这么组织：

设计选择带来的好处
用序号引用，不用指针和字符串数据连续、缓存友好、运行期不申请内存；整份可复制，也便于落盘做确定性回放
执行顺序预先排好每帧只做一次线性遍历，没有临时判断
逻辑中间图与物理画布分开复用只改一个编号；多个效果往往只需少数几块画布
参数布局与参数值分开调参、时间轴动画都不触碰编译结果，所以不用重编译
编译结果只读天然线程安全；每帧新建的只是从池里取的画布句柄

同类渲染图系统大体都是这个形状：一张步骤表 + 一张资源表 + 可复用的画布编号。规模更大时可把几张表合成一整块连续内存、改成按列存储，或把编译结果缓存成二进制以跳过重复解析；MVP 阶段按上面的表组织就够了。更细的编译与执行见 5.5，参数下标见 5.3，画布复用见 7.1。

目标、边界与决策速览

Scope
一句话方案：不要试图「复刻一套成熟特效 SDK」。先交付一个时间戳驱动、素材描述、GPU 零拷贝、能接真实相机、多平台可跑的最小内核，把渲染图、资源池、调度契约这三根支柱立稳，再按能力阶梯叠加脚本、AI、后编辑与产品化。这类引擎值得学的是结构性决策，而不是它的规模。

1.3 明确的非目标（防止 scope 失控）

不做

不自研模型与训练

人脸、分割、深度等一律视为外部模型插件，引擎只定义接口、前后处理与调度。模型可换、可裁剪、可缺位降级。

不做

不追求专业动效格式全兼容

不实现 AE 表达式引擎与完整时间特效体系。动画用「关键帧 + 缓动 + 参数轨道」表达，够用且可测。

不做

不做创作工具与相机 App

素材由外部工具生成 JSON；相机权限、会话、对焦曝光由宿主负责。引擎只消费素材与纹理。

不做

不一次性覆盖全部平台

先「桌面 + 一个移动端」，M1 再引入第 2 个移动平台，用来倒逼平台抽象是否真的干净。

1.4 统一验收口径

所有里程碑都用同一把尺子，避免「能跑」被当成「做成」：

确定性同素材 + 同输入帧 + 同时间戳 → 像素一致
零增长连续 1000 帧显存与句柄数不单调上升
可降级关掉任一特性仍能编译、仍能出图
可回放API 调用序列落盘后可离线复现
前提假设：2~3 名有图形 / 移动端经验的工程师；输入由宿主提供（相机或解码后的纹理）；目标 30fps 起；允许使用成熟开源库，但不依赖不可替换的二进制黑盒。若团队已有自研 RHI 或脚本系统，可替换本文对应选型，接口契约保持不变。

总体架构

Architecture

3.1 六层结构

A
API 层 — include/fx/：Engine / FrameDesc / IRenderTarget；稳定的 C++ ABI 边界，宿主唯一可见部分
C
核心层 — core/：Scheduler（System 调度）、IStateStore（运行时状态）、FrameContext、AssetLoader、Timeline、Profiler
G
渲染层 — render/：IGraphicsDevice（包装 bgfx）、RenderGraph 编译器与执行器、FrameBufferPool、RendererPool、内置 Pass（含 NormalizePass）
F
能力层 — effects/（Shader + Pass 参数）、ai/（探测器插件）、media/（解码 / 导出，可选）
P
平台层 — platform/：图形上下文、外部纹理导入（OES / NV12 / PixelBuffer）、Present、文件路径、日志。只实现纯虚接口，不含业务逻辑
D
数据层 — schema/：素材 JSON Schema、参数定义、代码生成器、版本迁移器；构建期产物供 A / C / F 层共用

依赖方向：宿主 → A → C → G / F → P（P 只实现 C、G 定义的接口），D 层在构建期横向生成代码。禁止能力层反向依赖 API 层；禁止 Shader 与 Pass 直接读写状态存储，只能通过参数表。

3.3 六条设计原则

时间戳是唯一驱动：RenderFrame(t, frame) 是「给定 t 求一帧」的纯语义。禁止 System 读墙钟或累加 dt；相机预览也只是把 pts 作为 t 传入。
效果即数据，Pass 即函数：素材描述执行哪些 Pass 及其参数；Pass 只接收输入纹理 + 参数 + 输出目标，不持有跨帧可变状态。
渲染图先编译再执行：拓扑排序、资源别名、依赖校验在素材加载期一次完成；每帧只遍历，热路径不做字符串查找与动态分配。
GPU 句柄全程流转：外部纹理只导入不拷贝；中间结果全是 FrameBuffer 句柄；CPU 回读只在显式 ReadPixels 时发生。
状态单线程写、AI 快照只读：IStateStore 只在渲染线程修改；AI 结果以不可变快照发布，避免到处加锁。
任何能力都可缺席：脚本、AI、3D、导出都是可选特性；缺位时编译通过，素材加载给出明确降级提示，而不是崩溃。

4.2 决策一：要不要引入 ECS 底座

先区分两个问题：「ECS 范式」有没有必要，和「某个具体 ECS 库」有没有必要。结论分三层，先看成熟引擎里可以观察到的现象。

① 事实：这类引擎实际用到了 ECS 的哪些能力

ECS 库通常提供使用情况可观察现象
实体 / 组件存储重度：素材按类型名反射成上百种组件并挂到实体素材是数据驱动的，组件类型随业务持续增长
按组件组合查询极重度：组合查询在处理单元中出现百处以上，单个 AI 处理单元即数十处各处理单元普遍依赖「按条件筛出一批实体再批量处理」
事件总线使用：发布 / 订阅贯穿处理单元、脚本与平台层跨模块靠事件解耦，而不是互相直接调用
处理单元的调度管理完全弃用：不使用框架自带的调度器引擎自己维护若干条执行队列，手写注册与逐帧更新，注册顺序即优先级
处理单元基类被大幅改造：加入启用开关、重置、名称、耗时统计等字段框架提供的基类已被改造成接近自有类型

也就是说，真正被依赖的是 ECS 的「动态组件容器 + 组合查询 + 事件总线」，框架最核心的调度反而被整套替换。以上只归纳架构层面的现象，不涉及任何具体实现。

② 三层结论

对成熟引擎

ECS 范式：有必要

上百种组件任意组合（继承树会爆炸）、百处以上「按组合批量处理」、脚本按字符串读写任意组件、运行时增删子树——这四点都是 ECS 的天然能力，不是过度设计。

对成熟引擎

具体某个 ECS 库：不必要

这类库主要提供稀疏集存储与事件总线，业界同类实现（EnTT、flecs）或自研 sparse set 都能承担。成熟引擎弃用其调度器、改造其基类，本身就说明它只是可替换的数据层。

对自研 MVP

ECS 范式：暂不需要

本方案用显式 RenderGraph + 固定参数表。传统 ECS 里「找所有带 X 组件的实体」，在这里变成「Graph 第 N 个 Pass 显式读 @ai.face」——查询需求被数据结构的显式化消解了。

代价要说清：此时引入 ECS 只剩成本（间接层、类型擦除、调试困难、学习成本）。但如果后期要做可视化编辑器、组件热插拔、脚本按名访问、嵌套子素材，再迁移也有成本。所以决策不是「永不引入」，而是延迟决策 + 留好隔离边界：所有状态读写只经过 IStateStore（接口见 5.3）。

4.3 决策二：摄像头预览要补哪些选型

预览是 push 模型（相机推帧），存在外部纹理格式差异、方向与生命周期约束，而且通常是第一个真实场景。它必须在 L0 / M0 就跑通，否则 RHI 抽象与帧接口会被迫返工。

业界常见的做法（可参照）

  • 对外只留一个相机纹理入口，把纹理句柄、宽高、设备朝向、图像原点一起传入；传感器朝向与渲染尺寸另有独立配置，旋转用 0 / 90 / 180 / 270 四档枚举表示。
  • 相机朝向、传感器朝向、纹理原点、渲染尺寸分开配置，不塞进每个 Shader；由输入预处理环节做旋转 / 裁剪归一，产出一张规格统一的中间纹理。
  • 平台侧先把各形态的相机纹理（外部纹理、YUV、像素缓冲等）统一成普通 2D 纹理，再交给内核，因此内核只面对一种纹理形态。

子问题选型理由

外部纹理平台层的「外部纹理导入」+ Graph 第 0 节点 NormalizePass屏蔽 OES / NV12 / CVPixelBuffer / RGBA 差异，一次转换后全链路只认 RGBA8

  • 加载期做完所有昂贵工作：Schema 校验 → 版本迁移 → 资源存在性 → 能力声明比对 → Graph 编译（5.5）→ 参数键解析为整数索引（5.3）。运行期不做字符串解析。

5.5 RenderGraph：先编译，后执行

渲染图承担常见实现里「渲染树 + FBO 乒乓 + 渲染器池」三者的职责，但用显式图 + 编译期资源分析替代运行期隐式推导。

1
编译（素材加载时一次）：展开 Input 节点（插入 NormalizePass 作为第 0 节点）→ 按 in/out 建边 → 拓扑排序 → 检测环与悬空引用 → 计算每个 RT 的生命周期区间 → 对不重叠的 RT 做别名复用 → 实例化 Pass 并固定 uniform 布局。
2
执行（每帧）：按拓扑序取输入纹理 → 从池里按「宽、高、格式」取一张输出画布 → 执行该 Pass（图形设备、输入、输出、参数）→ 归还上游引用 → 输出成为下一节点输入。
3
输出：Output 节点决定最终纹理；Present 负责上屏缩放、Y 翻转、alpha 预乘；导出模式跳过 Present，直接把纹理交给编码器。
NormalizePass

Graph 的第 0 节点

输入外部纹理（OES / NV12 / PixelBuffer / RGBA），按 transform 与 mirrored 做旋转、镜像、裁剪，缩放到处理分辨率，输出标准 RGBA8。此后所有 Pass 与 AI 都不感知平台差异。输入已是标准 RGBA 且无变换时退化为直通。

RT 别名

为什么必须做

5 个 Pass 的朴素实现需要 5 张全尺寸 FBO（1080p RGBA 约 40MB）；做生命周期分析后通常只需 2~3 张。这是移动端显存峰值最关键的优化，且必须在编译期算好，运行期只做池分配。

6.1 五阶段流水线

① Prepare（渲染线程）帧缓冲池回收上一帧句柄；InputImport 零拷贝导入外部纹理并执行 NormalizePass；AssetSync 写入宿主参数输入：FrameDesc / t · 输出：标准 RGBA8 纹理 + 待求值参数
② Simulate（渲染线程）Timeline 按绝对时间 t 求值所有参数轨道；更新锚点与事件禁止读墙钟；随机源由 t + assetId 派生
③ Detect（非阻塞投递）DetectorSubmit 把归一化纹理 + Fence 投给 DetectorHub，按依赖分派到 worker；立即返回，绝不等待渲染消费「最近一次已发布快照」，允许错 0~1 帧
④ Render（渲染线程）GraphExecute 按编译序列逐 Pass 执行，FBO 从池中取还Pass 只读参数表与 AI 快照，不持有跨帧可变状态
⑤ Present / Output上屏或返回 TextureId；导出模式跳过 Present；记录 trace、帧耗时、队列长度、显存峰值输出：上屏 / 结果纹理 / 显式回读

为什么 NormalizePass 放在 Prepare 而不是 Render：Detect 阶段的 AI 也需要标准朝向的 RGBA 输入，提前归一化后两者共享同一张纹理，省一次转换。

6.3 场景：摄像头预览链路

预览是 push 模型，但通过「pts 即 t」被无损装进上面的纯函数式流水线，引擎内部没有任何预览专用分支，只多了 NormalizePass 一个节点。

① 宿主相机回调拿到外部纹理 + 帧 pts + 传感器方向 / transform；只保留最新一帧（深度 1）Android: SurfaceTexture(OES) · iOS: CVPixelBuffer(NV12/BGRA) · 桌面: RGBA8
② 宿主 GL 线程调用RenderFrame(pts, frame)，frame 中填 kind / transform / mirroredt 就是相机 pts；预览与后编辑走同一入口
③ Prepare：导入 + 归一化ImportExternalTexture 包装句柄 → NormalizePass 输出标准 RGBA8（处理分辨率）此后 AI 与所有效果 Pass 不感知平台纹理差异
④ Detect / Render / PresentAI 异步消费；效果链执行；上屏或回传结果纹理掉帧时宿主侧直接丢弃旧帧，引擎不排队

6.4 时间语义与 seek

纯函数式求帧

RenderFrame(t) 的输出只依赖 t、素材、输入帧、AI 快照。seek / 倒放 / 变速都只是换一个 t 映射：sourceTime = Remap(t, timeEffect)，无需重置引擎。

AI 是唯一的非纯部分

把结果连同 frameTime 一起归档，回放时按时间戳取对应快照（缺失则 last-good），从而保证回放仍可复现。

帧预测与预解（L4）

后编辑场景由 Decode worker 按 t + 1/fps 预解下一帧，放入深度 1 的队列；命中则省一次解码，未命中直接同步解。

暂停 ≠ 停止帧循环

后编辑暂停时固定 pausedTime 继续调用 RenderFrame(pausedTime)，画面仍可响应参数热更新。注意区别于 OnPause()：后者是退后台、释放资源。

6.5 线程模型与同步

线程职责同步方式禁止事项
渲染线程（宿主 GL 线程）帧驱动、IStateStore 写入、Graph 执行、Present无锁（单线程）不得等待 AI 结果
AI worker × N模型推理、前后处理有界队列 + GPU Fence（不可用时降级为强制同步等待）+ 不可变快照不得写状态存储、不得创建 GL 资源
Decode worker（L4）视频 / 图片预解码深度 1 队列 + 共享上下文不得触碰渲染图
RHI 线程（可选）命令录制与提交双缓冲 FrameContextMVP 阶段不引入
强约束：GL / Metal 资源只能在持有上下文的线程创建。AI 若需 GPU 推理，应使用共享上下文 + Fence，或在 CPU 后端跑小模型；跨线程直接传裸 texture id 而不同步，是这类引擎最常见的花屏来源。

Pass 实例与 LUT、贴纸等静态纹理按素材生命周期缓存；素材卸载时整批回收，避免「卸载后显存不降」。

别名

Transient RT 复用

编译期计算每个 RT 的首次写入 / 末次读取区间，不重叠者复用同一物理 FBO（原理见 5.5）。显存峰值的主要控制手段，M1 必须落地。

生命周期

三级所有权

引擎级（设备、池）、素材级（Graph、Pass、LUT）、帧级（transient FBO、AI 快照、导入的外部纹理）。每级有明确 Release()，销毁顺序自帧级向上。

7.2 外部纹理与前后台

  • 所有权约定：宿主创建、宿主销毁；ImportExternalTexture 只生成本帧有效的包装，不接管、不缓存、不删除。宿主在帧间复用同一纹理 id 时，用 hostFrameIndex 区分，以便 trace 与 fence 正确关联。
  • 退后台：OnPause() 撤销 AI 任务、清空 FrameBufferPool 与 transient 资源，只保留素材级 CPU 数据；OnResume() 重建 GPU 资源后再接受 RenderFrame。
验收方法：连续 1000 帧记录 allocatedFBO / textureBytes / handleCount 三条曲线，必须稳定在平台期；素材反复装卸 50 次后显存回到基线 ±5%；前后台切换 20 次不黑屏、不泄漏。

9.1 架构：一个内核、三类插件、两条边界

整套引擎可以压缩成一句话：一个只认时间戳的内核，按加载期编译好的表驱动三类插件；宿主被挡在 ABI 边界之外，可选能力由构建期边界决定是否存在。

一个内核

内核只做三件事

持有帧循环（Scheduler 的五个阶段）、持有运行时状态（IStateStore）、执行编译好的渲染图（RenderGraph 执行器）。内核不认识任何具体效果、模型或平台。

三类插件

Pass · Detector · Platform

三类插件的接入方式相同：实现接口，再注册到表里。内核只按名字或特性查表装配，新增插件不改内核（见 8.1 的四要素）。

两条边界

ABI 边界 · 构建期边界

宿主只能看到 Engine 和 FrameDesc（5.1）。features.json 决定哪些插件进包；缺席的插件由 no-op 实现顶替，调用方无需写条件编译（10.1）。

插件接口如何注册内核何时调用缺席时
效果 Pass输入纹理 + 参数 → 输出纹理，无跨帧状态注册宏写入 Pass 工厂表Render 阶段，按执行顺序表逐步调用加载期标记为空操作，并上报一次
探测器IDetector（5.6）由 DetectorHub 按特性装配Detect 阶段投递，worker 线程里执行空探测器中心，快照恒为默认值

9.3 线程与通信通道

线程职责见 6.5，这里只讲线程之间怎么传数据。全系统只有 5 条通道，每条都有明确的方向、容量和生效时机；不存在第 6 条「顺手共享一下」的路径。

通道方向实现建议满了 / 冲突时何时生效
① 相机帧槽相机回调 → 宿主 GL 线程宿主侧单槽「最新值」新帧覆盖旧帧下一次 RenderFrame
② 命令队列任意宿主线程 → 渲染线程MVP 用「互斥锁 + 双缓冲数组整体交换」，之后可换无锁多生产者队列同一参数多次设置，只保留最后一次下一帧 Prepare 统一生效
③ AI 任务队列渲染线程 → worker有界环形队列，深度 2；任务携带纹理、t、Fence、代际号丢掉最旧的任务，并归还其纹理worker 空闲即取
④ 快照槽worker → 渲染线程原子替换引用计数指针，每个探测器一个槽新快照覆盖旧快照；代际号过期则直接丢弃渲染线程下一次读取时
⑤ 回收通道worker → 渲染线程复用 ② 的命令队列（「归还纹理」指令）—下一帧 Prepare 归还 GPU 纹理

下图把三条线程放在同一时间轴上：渲染线程每 33ms 跑一轮五阶段；AI 推理偶发变慢时，渲染线程继续使用旧快照，不会为此停下。

读图要点：① 相机帧和 SetParam 都只在 Prepare 进入渲染线程，一帧之内参数不会中途变化；② 投递是非阻塞的，推理与渲染并行；③ 渲染开始时读到哪一份快照就用哪一份，帧 N+2 渲染时 N+1 的推理还没完成，就继续用快照 N（错 2 帧），画面照常输出。持续变慢时由 8.3 的错帧与退档策略接管。

把 9.3 的 5 条通道落到代码里，只需要下面这些函数。注意哪里会「等待」：只有 worker 和生命周期函数会等，渲染线程任何时候都不等。

同步通信骨架 · 伪代码 
// ① 宿主任意线程：只入队，立即返回
函数 Engine.SetParam(passId, key, 值):
  inbox.推入(设参数{passId, key, 值})

函数 Engine.LoadAsset(字节):
  运行时 = 校验 + 迁移 + 编译(字节)          // 纯 CPU 工作，在调用线程完成
  若 失败: 返回 错误
  inbox.推入(切换素材{运行时})               // GPU 资源留给渲染线程创建
  返回 素材句柄

// ② 渲染线程 · Prepare：一次取出全部指令，之后本帧状态冻结
函数 处理指令(ctx):
  批 = inbox.整体交换()                      // 每帧只拿一次锁
  循环 批 中每条 cmd:
    若 cmd 是 设参数:   store.SetParam(查下标(cmd.passId, cmd.key), cmd.值)  // 同键后者覆盖
    若 cmd 是 切换素材: 创建 GPU 资源(cmd.运行时); current = cmd.运行时
    若 cmd 是 归还纹理: AI 纹理池.归还(cmd.纹理)

// ③ 渲染线程 · Detect：投递即返回
函数 投递检测(ctx):
  tex = AI 纹理池.取出()                     // 槽数 = 队列深度 + 1；取不到就本帧不投
  若 tex 为空: 返回
  缩放(ctx 中的归一化纹理 → tex, 检测分辨率)
  fence = device.插入Fence()                 // 标记「tex 已写完」
  hub.任务队列.推入(任务{tex, ctx.t, fence, generation})  // 满则丢最旧，并归还其 tex

// ④ 渲染线程 · Render：读快照不加锁
函数 执行渲染图(ctx):
  快照 = hub.快照槽.原子读取()               // 拿到即持有引用，本帧内不会变
  循环 current.steps 中每一步:
    执行该步(参数 = store, 锚点 = 快照)

// ⑤ AI worker：唯一在常态下会「等待」的线程
循环:
  任务 = hub.任务队列.阻塞取出()
  若 任务.generation ≠ generation:
    inbox.推入(归还纹理{任务.tex}); 继续      // 过期任务直接作废
  等待(任务.fence)                           // worker 等 GPU；渲染线程不等
  结果 = 探测器.Run(任务.tex)
  inbox.推入(归还纹理{任务.tex})             // GL 对象回到渲染线程处置
  hub.快照槽.原子替换(冻结(结果, 任务.t, 任务.generation))  // 旧快照引用归零后自动释放

// ⑥ 生命周期：仅有的同步点
函数 Engine.OnPause():
  generation += 1                            // 之后到达的旧结果一律丢弃
  清空任务队列; 等待进行中的推理结束         // 最多等一次推理耗时
  释放临时资源与 AI 纹理池
为什么不用锁

锁只剩一把

命令队列的锁每帧只拿一次，持有时间是一次数组交换；快照槽是原子指针替换。渲染热路径上没有锁，也就不存在优先级反转和死锁。

为什么要 Fence

CPU 先到，GPU 未完

渲染线程提交「缩放到 tex」后立即返回，此时 GPU 可能还没写完。worker 必须先等 Fence 再读 tex，否则读到半帧数据，表现为花屏或检测框抖动。

为什么要代际号

退后台后的「迟到结果」

OnPause 之前投出的任务，结果可能在回前台后才到。代际号不一致就直接丢弃，避免旧结果覆盖新会话的快照。

9.5 七条不变量（代码评审清单）

时间只从参数 t 进入：任何模块都不读墙钟、不累加 dt（3.3、6.4）。
结构只读：素材运行时、工厂表、System 序列一旦构建完成就不再修改；要变就整体重建，再在 Prepare 中切换引用。
值只有一个写者：状态存储只在渲染线程写；宿主的修改一律经命令队列，在 Prepare 统一生效，保证同一帧看到的参数一致。
结果不可变：AI 快照发布后只读；跨线程只传消息或不可变快照，绝不传可变对象的引用。
队列有界，满了丢旧：任何队列都不能让生产者阻塞，也不能无限增长。
渲染线程永不等待：等待只发生在 worker（等 Fence）以及 OnPause / Release（等推理收尾）。
GPU 对象只在渲染线程创建和销毁：其他线程拿到的纹理必须配 Fence 使用，用完经回收通道交还。
与其他章节的关系：本章是 03（分层）、05（接口契约）、06（一帧执行，以及 6.5 线程表）、07（资源所有权）的收束版。落地节奏按 12 章：M0 只需命令队列和生命周期（伪代码 ①②④⑥），M3 再补齐 AI 的任务队列、Fence、快照槽和代际号（③⑤）。

Trace 设计

每帧输出一条 Chrome Trace：Phase 分段、每个 Pass 的 GPU / CPU 耗时、AI 任务从投递到发布的年龄、FBO 分配归还、降级事件。由 FrameContext.trace 自动打点，业务代码零侵入。

诊断开关

FX_DUMP_FRAME_GRAPH（导出 Graph dot 图）、FX_DUMP_SHADER、FX_FORCE_CPU_DETECTOR 等环境变量级开关，让线上问题可在本地复现。

分阶段实施路线

Roadmap

工期为量级估算（2~3 名熟悉图形与移动端的工程师，单位：人周），用于排优先级而非承诺交付日期。每个阶段都必须产出可演示、可回归的增量。

M0 · 4~6 人周 · 目标 L0

最小可跑内核 + 真实相机预览

  • CMake + bgfx + 桌面 GL；定义 Engine / FrameDesc / IPlatform / IRenderTarget。
  • RenderFrame(t, frame) 时间戳驱动、外部纹理零拷贝导入、一个 LUT Pass、Present；FlatStateStore。
  • NormalizePass + 一个移动端的相机接入（OES 或 CVPixelBuffer）+ OnPause / OnResume（见 4.3、6.3）。
  • trace 与最简 profiler；第一张金样图。

验收：同 t 出图一致；1000 帧无句柄泄漏；修改 LUT 素材 JSON 即生效；相机预览 30fps、旋转 / 镜像 / 裁剪正确、前后台切换不黑屏。

M1 · 8~12 人周 · 目标 L1

渲染图与资源管理

  • Schema 校验器、Graph 编译器（拓扑排序 / 环检测 / RT 别名）、FrameBufferPool / RendererPool。
  • 补齐 3 个效果（LUT、可分离高斯、混合贴纸）与 REGISTER_PASS 注册表；素材热加载 / 卸载。
  • 引入第 2 个移动平台，用平台差异倒逼 IPlatform 抽象收敛。

验收：5 Pass 串联时 FBO 数 ≤ 3；两平台金样图在容差内一致；素材装卸 50 次显存回到基线。

M2 · 8~12 人周 · 目标 L2

内容层：特效不再需要改 C++

  • params.yaml + 代码生成器：产出 C++ 结构体、参数校验器、Schema 片段、脚本文档。
  • 时间轴 / 关键帧 / 缓动求值、SetParam 热更新、requires 能力声明与降级、版本迁移器。
  • 可选接入 QuickJS：只暴露「读参数、写参数、发事件」三类能力（经由 IStateStore），不暴露 RHI。

验收：新增组合特效只提交 JSON + 已有 Pass 参数；老素材自动迁移成功；脚本关闭时 min profile 全绿。

M3 · 8~14 人周 · 目标 L3

智能层：AI 异步与稳定化

  • IDetector / DetectorHub：有界队列、Fence 同步、丢旧帧、不可变快照、last-good、依赖链。
  • 接入人脸关键点、人像分割 2 个探测器与对应效果；解析 @ai.* 锚点引用。
  • 时域平滑、错帧切换、三级退档；队列年龄与取帧策略纳入 trace。
  • ECS 评估点：按 4.2 的升级信号检查，满足两条才把 FlatStateStore 换成 EnTTStateStore。

验收：30fps 下 AI 不阻塞渲染；注入 100ms 推理延迟时画面稳定无撕裂；模型缺失时素材降级出图且只上报一次。

M4 · 10~16 人周 · 目标 L4

产品化：后编辑、导出、矩阵

  • 后编辑时间语义（seek / 变速 / 倒放 / 暂停）、Decode worker 帧预测、音视频同步与导出编码。
  • features.json 四级裁剪 + CI 特性矩阵；Android JNI / iOS OC 门面；包体与启动耗时基线。
  • 全量金样图、确定性回放、素材 fuzz、性能回归门禁。

验收：全矩阵 CI 绿；min / lite / full 三档包体差异可解释；回放逐像素一致。

M5 · 持续 · 能力扩充

效果库与高级能力

按「四要素」规范扩充效果库；此时才评估 3D / 物理 / 完整脚本 DSL / 更多模型等重资产方向。原则：任何新能力都必须能缺席，且不得破坏 M0 定义的接口契约。

量级结论：到「可演示 MVP（M0+M1）」约 3~4.5 人月；到「带 AI 的可用版本（M0~M3）」约 7~11 人月；到「产品化（M4）」约 10~15 人月。不追求一次对齐成熟引擎的规模——那是多年业务累积的结果。

B · 概念对照（与《架构设计概要》）

本方案业界 / 成熟引擎中的常见做法差异
Engine.RenderFrame(t, frame)由输出对象按时间戳拉取一帧；相机纹理另走单独入口合并为单一入口，输入纹理随帧传入
Scheduler + Phase引擎内部按注册顺序维护的多条处理单元执行队列显式 order 与依赖拓扑，取代隐式注册顺序
IStateStoreECS 的实体与组件存储接口隔离；MVP 为扁平实现，按需换 EnTT
NormalizePass输入预处理环节 → 规格统一的中间纹理作为 Graph 第 0 节点，AI 与效果共享输出
显式 renderGraph组件树 → 树构建环节 → 渲染树去掉中间推导层，编译期做别名分析
FrameBufferPool帧缓冲池 + 取用辅助函数思路一致，改为自有接口 + 上限降级
DetectorHub / 快照AI 能力单元 + 数据中转模块接口更小，模型完全外置
features.json多套 JSON 配置 + 构建期宏注入单一事实源 + no-op 实现
